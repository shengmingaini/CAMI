# 从「42 个任务」到「能玩的游戏」——缺口路线图

> 结论先行：**完成 42 个任务 ≠ 得到一个游戏**。
> 42 个任务交付的是「服务器端基础框架 + 极简客户端骨架 + 性能/容灾验证」，约等于一个可玩 MMORPG 的 **20–25%**。

---

## 1. 完成 42 个任务后，你手上有什么

**有的（可验证、可演示）**

- 四进程服务端：Gateway / GameNode / DataService / ControlService（TASK-040 补齐最后一块）
- 核心系统：Entity / Scene / 20Hz Scheduler / AOI / Movement / Combat / Buff / Skill / Quest / Inventory / Economy / Lua 热更 / Social
- 数据层：Redis + MySQL，账本与幂等
- 性能数字：1k 战斗 Tick P95/P99（TASK-025）、50k CCU 七级阶梯（TASK-038）
- 容灾：断线重连、Session 恢复（TASK-037）
- 客户端骨架（**规格待重写**）：Client Core / 渲染器 / 资源与低配（TASK-034/035/036）
  → 原规格为「自研 D3D11」，与已批准的 **Godot 4.7.1 + 2D** 冲突；按 RFC §9.8 在服务端与游戏核心完成后再重写。
  → 即便按现规格交付，它也是 **验证用客户端**（能跑通链路），**不构成可玩**——见下方「没有的」。

**没有的**

- 玩家能看懂的画面、能上手的操作
- 任何游戏内容：职业、技能数值、装备、掉落、任务文本、剧情、地图
- 任何美术与音频资产
- 任何运营外围：账号、区服、公告、GM、反外挂

一句话：Bot 能跑通完整链路，**人不能玩**。

## 2. ✅ P0 阻塞点：客户端技术路线（已解决，2026-09-10 关闭）

> **状态：已关闭。** 决策链完整：2026-08-29 定引擎（Godot 4.7.1）；2026-09-10 定形态（**2D 优先，现阶段不做 3D 几何模型**）。
> 权威记录见 `mmorpg_tasks/docs/rfc/client-engine-selection.md` §7.1 / **§9（追加决策：2D 优先）**。
> 本节保留为决策沿革，**不再构成开工阻塞**。

核对任务包时发现的真问题：任务包规格与已批准路线冲突。

| 来源 | 路线 |
|---|---|
| **本任务包 TASK-035** | 明确「选定后端 **D3D11**，预留 Vulkan 抽象层但不实现」+「**禁止引入重型第三方引擎**（保持轻量）」→ 即**自研轻量渲染器** |
| **你的另一份 MMORPG 规划**（记忆） | 候选引擎收敛于 **Godot**（2D+3D）与 **Phaser 3** |
| **RFC 结论**（2026-08-29 → 09-10） | **Godot 4.7.1 + 2D（已批准）**，见 RFC §4.6 / §6.1 / §9 |

四条路线的评审结论：

- **Phaser 3** 是 2D Web 引擎（Canvas/WebGL），与「D3D11 原生渲染器」不兼容，且 Web 技术栈与 C++ 服务端/协议层零复用 —— **已排除**。
- **自研 D3D11** 与任务包一致，但需自研渲染器 + 资源系统 + 窗口/生命周期，而 TASK-034~036 只给了 3 个任务的预算 —— 严重低估，**已否决**。
- **Godot 4.7.1 —— 当前路线（已批准）**：全文本工程（.tscn/.tres/.gd）、AI 可直接生成/校验 GDScript、编辑器秒开、免激活、完全离线（绕过代理墙）、MIT 免费；通过 GDExtension(C++) 下沉协议/热路径，**C++ 复用不受损**。
- **Unity 6.3 LTS（URP）—— 可选回切**：若未来企业代理解除，可重新评估。保留为 RFC §6.2，无需重开 RFC。

**决策结论**：
1. 2026-08-29 —— 企业代理冒烟测试预检确认 Unity 安装/激活路径整体被拦（致命前置触发）；用户选择 **Godot 4.7.1**（单 ZIP 离线、免激活，仅编辑器下载需一次性联网）。
2. 2026-09-10 —— 用户追加形态约束：**2D 优先，现阶段不做 3D 几何模型**。此约束**强化**了 Godot 路线：RFC §5.2/§7.1 登记的 Godot 最大风险是「大规模 3D 流式 + 烘焙光照短板」，2D 阶段该风险**归零**；同时 3D 几何/贴图生产正是整链最大不可自动化项（AI 不生成 3D 几何模型本身），避开它等于拿掉关键路径上唯一无法靠加班解决的瓶颈。
3. **副作用**：TASK-035 的 D3D11 字面出现仅 2 处（一个枚举默认值 + 一条实施步骤），但 034-036 的整体前提是「自研 C++ 客户端 + 自研渲染器 + 自研资源系统」，与 Godot 自带能力全面重复 → 三份任务书**需重写**（时机见 RFC §9.8：服务端与游戏核心完成后再做）。
4. **下一步**：TASK-034/035/036 按 RFC §6.1 + §9 重写为 Godot 2D 规格 + 补出 12~16 个客户端任务（原估 15~20，2D 省掉 3D 资产管线）。

## 3. 缺口分层（P0 → P3）

### P0 · 让它「像游戏」——客户端（缺 12~16 个任务）

> **执行状态（2026-09-10 更新）**：客户端 P0 缺口当前**执行延后**——用户决策先搭服务端 + 游戏核心、暂不安装任何客户端引擎（见 RFC §7.2-1、§9.8、`docs/engine-agnostic-architecture.md`）。引擎与形态均已确定（**Godot 4.7.1 + 2D**），待需要表现层时按 RFC §6.1 + §9 补出。
>
> **任务数修正**：原估 15~20 → **12~16**。2D 规格省掉 3D 专属部分（蒙皮/骨骼动画管线、光照与烘焙、3D 地形与 NavMesh、LOD 制作、材质系统复杂度）；工作量主体（网络与同步、输入相机、UI 全套、音频、场景加载、打包流水线）不变——**省下的主要是资产管线，不是代码量**。

现有 TASK-034/035/036 只覆盖 Client Core / Renderer / Resource。**缺失**：

| 缺口 | 说明 |
|---|---|
| 网络与同步 | 协议对接（Protobuf/FlatBuffers）、状态同步、**客户端预测与插值**（手感生死线） |
| 输入与相机 | 键鼠/手柄输入、第三人称相机、碰撞与避让 |
| 角色表现 | 角色控制器、动画状态机、蒙皮/骨骼 |
| 战斗表现 | 技能释放、特效/粒子、伤害飘字、血条/目标框、受击反馈 |
| UI 系统 | 登录/选角、主界面、技能栏、背包、角色面板、地图、聊天、设置 |
| 音频 | 音效/BGM 系统与资源管理 |
| 场景 | 地形/场景流式加载、NavMesh 客户端侧、寻路 |

### P1 · 让它「有内容可玩」——内容与数值（缺 12~18 个任务）

**关键认知**：TASK-017/018/019/021 提供的都是**系统框架**，不是内容。框架跑空表 = 没有游戏。

| 缺口 | 说明 |
|---|---|
| 数值体系 | 职业、等级、属性成长、技能数值表、战斗公式（建议 Excel/JSON 配置驱动） |
| 场景内容 | 地图、地形、刷怪点、传送点、安全区 |
| NPC / 怪物 | 模型、AI 行为树配置、属性表、掉落表 |
| 任务与剧情 | 任务链、对话文本、剧情（中文文本量极大） |
| 装备与经济 | 物品表、装备词缀、合成/强化、掉落概率、商城定价、经济平衡 |

> 强烈建议：内容全部走**配置驱动**（Excel/JSON → 生成器 → 二进制），禁止硬编码进 C++。这是唯一能让 1 人维护的方式。

### P2 · 让它「能运营」（缺 8~12 个任务）

| 缺口 | 说明 |
|---|---|
| 账号体系 | 注册/登录/鉴权/多区服/角色槽 |
| 运营后台 | 公告、活动配置、GM 命令与后台、封禁 |
| 安全 | 反外挂、协议加密、行为审计 |
| 可观测 | 日志采集、监控告警、Trace、玩家行为分析 |
| 社交 UI | TASK-039 只做服务端逻辑，组队/好友/公会/聊天/邮件的**客户端 UI** 全部缺失 |

### P3 · 让它「好玩且稳」（长期）

- 真实玩家小规模测试（**Bot 数据 ≠ 真人体验**，手感/延迟/卡顿只有真人能验）
- 数值平衡迭代、手感调优、美术打磨
- 副本/战场/竞技场内容（TASK-020 只是 Instance 框架，内容为 0）
- Phase 2：Live Scene Migration（已登记 RFC）、跨服、赛季

## 4. 建议的里程碑：先做「垂直切片」

不要横向铺完服务端再铺客户端。对 1 人 + 每天 1–2 小时的节奏，**垂直切片**是唯一可行路径：

> **垂直切片 = 1 个职业 + 1 张小地图 + 1 个副本 + 完整战斗循环 + 能存档**
> 目标：一个真人能登录、打怪、升级、捡装备、下线再上线还在。

切片完成后再横向扩：加职业 → 加地图 → 加副本 → 加内容量。

**价值**：用最小代价验证「好不好玩 + 架构对不对」，避免做完 42 个任务才发现手感崩了或架构跑偏。

## 5. 工作量与现实提醒

| 项 | 估算 |
|---|---|
| 现有任务 | 42 |
| 需新增（客户端 + 内容 + 运营） | **+45 ~ +60 个任务** |
| 合计 | 约 **90 ~ 110 个任务**才算「能玩的游戏」 |
| 美术/音频资产 | **不是任务，是资产生产**——外购 / AI 生成 / 素材站，是最大不可自动化部分 |

**关于节奏的诚实提醒**：你每天只有 1–2 小时。原规划「60 周 / 约 300 工作日」若按全职 8 小时估，则约 2400 小时；按每天 1.5 小时折算约 **1600 个自然日（4 年+）**。要么压缩目标规模（先做一个「小型 MMORPG」而非「类魔兽世界」），要么把美术/内容外包或用 AI 规模化生产。**这个账建议现在就算清楚，比后面撞墙强。**
