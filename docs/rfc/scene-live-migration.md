# RFC · Scene Live Migration（场景实时迁移）

> 状态：**已登记（Planned / 第二阶段）**
> 关联任务：TASK-037 §1 / §8（第一版明确**不做** Live Scene Migration，仅做 Checkpoint 恢复）
> 登记日期：2026-09-10

## 1. 背景

TASK-037 第一版 Scene 恢复（37.4）采用**最近 Checkpoint 重建**语义：GameNode 崩溃后，Scene 容器在新
Owner 节点重建，玩家实时状态从 DataService 载入最近可靠持久化数据（默认 30s 一次 Checkpoint）。
玩家可能回到 30s 前的位置 —— 这是第一版可接受的设计妥协。

根规范 §1 将「Scene 可以独立迁移」列为长期目标，与 §34「第一版只要求重连 + 恢复」存在张力；本 RFC
记录该张力并约定：第一版按 §34 执行，Live Migration 作为第二阶段目标单独立项。

## 2. 目标（第二阶段）

- **零回退迁移**：GameNode 计划内/计划外下线时，Scene 的实时状态（玩家位置、NPC 状态、实体）**不丢失、
  不回退**，直接迁移到目标节点。
- **唯一 Owner 不双写**（PROJECT_REQUIREMENTS §10 / §12）：迁移期间通过 Command 切换 Owner，禁止两节点
  同时可写。
- **迁移对玩家无感**：迁移窗口内玩家连接不中断（或仅毫秒级停顿）。

## 3. 非目标（第一版已明确排除）

- 不做「恢复可能回退到 30s 前」的妥协（那是第一版的语义，本 RFC 要消除它）。
- 不引入 Redis 作为实时状态权威 Owner（§21 Forbidden）。

## 4. 候选方案（待第二阶段设计评审）

1. **状态快照流（Snapshot Stream）**：周期性 + 事件触发地把 Scene 增量状态推到目标节点热备。
2. **双活预热（Warm Standby）**：每个 Scene 在备份节点保有一个只读影子，主节点失效即时提升。
3. **一致性哈希重映射 + 增量同步**：结合 TASK-010 NodeRegistry 的一致性哈希，迁移时仅同步差异实体。

## 5. 风险 / 开放问题

- 迁移期间实体引用（EntityId）跨节点有效性。
- 大规模场景（kDefaultMaxEntities=100000）的增量同步带宽与延迟。
- 与 DataService 持久化节奏的协同（避免迁移与 Checkpoint 竞态）。

## 6. 验收（第二阶段另行定义）

- 计划内迁移：玩家零回退、连接不中断。
- 计划外崩溃：恢复点 = 崩溃瞬间（而非 30s 前 Checkpoint）。
- 无数据损坏：无重复物品、无负余额、无属性错乱（对账）。
